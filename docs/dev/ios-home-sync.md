## 数据与身份

Swift 使用 URLSession 调用同仓库 Nitro 的 `GET /api/home-screen` 和 `PUT /api/home-screen`。两者都要求现有 CloudBase 正式账号 Bearer token，服务端通过既有身份校验派生 UID，拒绝匿名和停用账号。客户端提供的 UID、文档 ID或 `_openid` 不决定读写对象。响应设置 `Cache-Control: private, no-store`。

沿用现有 NoSQL `user_home_screens` 集合，不另建用户身份或数据库。本轮只读核实集合索引：`_openid_1` 为普通索引，**并非唯一索引**；因此同时考虑同一用户的多份历史文档。未修改线上索引、规则或用户记录。

安装顺序、Dock 和最近使用继续使用既有 `appId` 引用。已有 slug 不强制重写；新增原生安装使用稳定记录 ID，旧 Web 目录已经支持精确记录 ID。接口不因某应用当前无法解析而删掉它，也不通过同步安装记录授予应用访问权限。

## HTTP 协议

GET 返回以下字段：

| 字段                          | 类型                  | 语义                                                        |
| ----------------------------- | --------------------- | ----------------------------------------------------------- |
| `schemaVersion`               | number                | 按客户端协商返回 1 / 2 / 3；原生当前请求 3                  |
| `revision`                    | string / null         | 文档身份、完整配置与更新时间的 SHA-256；不存在云居时为 null |
| `configuration.installedApps` | `{ appId }[]`         | 有序安装引用                                                |
| `configuration.dockApps`      | `{ appId }[]`         | 最多 4 个常用应用                                           |
| `configuration.recentApps`    | `{ appId, usedAt }[]` | 最多 100 个最近使用项，时间为毫秒                           |
| `configuration.updatedAt`     | number                | 服务端更新时刻；不存在云居时为 0                            |

没有云居时返回明确的空配置；查询失败或数据损坏不返回空配置。未知 schema、缺失修订字段、非法引用、HTML 响应或无效时间均不能被原生端视为成功。

PUT 提供 `baseRevision`（新建时必须显式为 null）、UUID `mutationId` 和 `configuration` 的三个引用数组。客户端更新时间不会决定覆盖顺序。安装项最多 1000 个、Dock 最多 4 个、最近项最多 100 个；单个标识最多 256 个 UTF-16 单元，各数组不能包含重复标识，时间必须为非负安全整数。

成功写入由服务端产生单调递增的 `updatedAt` 并返回完整新版本。原生端要求返回 schema 3、非空修订号，且引用、文件夹与来源均与本次提交一致，才确认上传成功。

| 状态 / 业务码                | 行为                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| 401                          | 原生尝试一次合并的令牌刷新，再以原账号重试；不转成访客请求 |
| 403                          | 当前账号不能同步，保留本地内容                             |
| 400 / `HOME_INPUT_INVALID`   | 参数不正确，不写入                                         |
| 409 / `HOME_CONFLICT`        | 附带当前云端版本，保留本地修改并要求比较选择               |
| 409 / `HOME_DATA_INVALID`    | 历史记录损坏或归属异常，保留原记录                         |
| 409 / `HOME_HISTORY_LIMIT`   | 历史记录达到 90 份，停止读写并要求检查                     |
| 409 / `HOME_MUTATION_REUSED` | 同一请求标识被用于不同内容，不接受重放                     |
| 503 / 网络失败               | 不确认成功，本地修改和请求标识继续保留                     |

## Schema 2：文件夹（2026-10-18）

文件夹以 `configuration.folders: { id, name, appIds }[]` 表示。**成员仍留在 `installedApps` 中**，文件夹显示在第一个成员的位置；不认识文件夹的客户端因此照常平铺显示所有应用，不会出现未知条目。

| 规则     | 内容                                                                                                                                                                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 版本协商 | `GET /api/home-screen?schema=2` 返回 `schemaVersion: 2` 并包含 `folders`；不带参数（旧原生、旧 Web）仍得到 schema 1，响应中没有该字段。PUT 在请求体中写 `schemaVersion: 2` 才会写文件夹 |
| 校验     | 最多 200 个；`id` 为 1–64 位字母数字 `_-`；`name` 去首尾空白后 1–40 字、无控制字符；`appIds` 非空、均在 `installedApps` 中、跨文件夹不重复。schema 2 写入违反任一项即 400，不静默修正   |
| 旧客户端 | schema 1 PUT 不带文件夹时，服务端**保留已存文件夹**，只去掉该次写入已移除的成员与因此变空的文件夹；Web 端直接用 CloudBase `update()` 只改应用数组，本身不触碰 `folders`（有单测锁定）   |
| 读取容错 | 存量数据中已不在 `installedApps` 的成员、重复成员在读取时去掉，空文件夹不返回；结构损坏仍按 `HOME_DATA_INVALID` 保护原记录                                                              |
| 修订号   | 两个 schema 共用同一修订号，并包含文件夹，因此只改文件夹也会让旧客户端得到冲突；没有文件夹的文档修订号与引入前完全一致，部署后不会产生虚假冲突。幂等哈希同理，旧请求记录仍可重试        |
| 原生端   | 当前请求 schema 3；仍能读取 schema 1 / 2。采用 schema 1 时保留本地文件夹并按新应用列表清理；旧响应不作为当前格式写入成功的确认                                                          |

本地快照新增可选 `folders`，旧文件可直接读取。固定 / 移除应用时自动离开所属文件夹，文件夹变空即消失。

## Schema 3：作者来源选择（2026-10-18）

后续 Goal 新增 `configuration.applicationSources: { appId, ownerLogin }[]`。仅记录用户选择的作者来源；没有条目表示市场来源。应用 ID 仍使用现有引用，来源不携带网址、token、访问范围或可信主机，不是运行权限。接收端实际打开前仍必须重新读取作者公开发布并检查免费公开条件，不能套用市场旧版本的报价或授权。

- `GET ?schema=3` 返回文件夹与来源数组；schema 1 / 2 响应保持原形状。schema 3 PUT 必须显式提供数组，空数组可明确切回市场版本。
- schema 1 / 2 写入保留存量来源，只移除不再出现在安装、Dock 或最近使用中的引用。旧客户端仍可能按市场内容打开该 ID；保留来源字段不代表旧客户端已经理解作者版本。
- 来源最多 1104 项，appId 唯一且必须在三个引用数组之一；ownerLogin 与既有原生作者服务格式一致（1–64 位 ASCII 字母、数字、`_.-`，排除 `.` / `..`）。来源只允许这两个字段，拒绝额外网址或权限字段。
- 同步按 appId 规范排序，来源变化纳入所有 schema 的同一修订号与 schema 3 幂等摘要。仅来源变化也阻止旧修订覆盖；没有来源的历史修订和原 schema 1 / 2 幂等摘要保持一致。
- 存储适配器复用现有验证身份、事务重读、固定账号文档和错误处理。结构损坏仍返回 `HOME_DATA_INVALID`，不以空数组覆盖。

未登录的访客云居可以在“云居同步”中逐台设备开启 **iCloud 同步**，默认关闭。登录云乐坊后仍走上面的账号接口，两份数据互不读写：账号云居从不写入 iCloud，iCloud 记录也不会进入账号云居。

| 规则   | 内容                                                                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 存储   | `NSUbiquitousKeyValueStore` 的 `home.guest.v1`，值为 schema 3 `RemoteHomeScreen` JSON；需要 `com.apple.developer.ubiquity-kvstore-identifier`，不建 CloudKit 容器或数据表 |
| 修订号 | 写入标识与内容（不含时间）的 SHA-256，与服务端同为 64 位小写十六进制；同一写入重试直接返回已存版本，旧修订写入得到冲突                                                    |
| 冲突   | 复用协调器的采用 / 上传 / 比较选择规则与界面。iCloud 没有服务端事务，两台设备同时写入时由 iCloud 以后写为准；另一台收到外部变更通知后按“无本地更改则采用”处理             |
| 保护   | 未比较过的非空访客云居不被 iCloud 版本静默替换；iCloud 记录为空或被重置时重新上传本机布局，不清空设备；iCloud 账号变化后先要求比较                                        |

| 开关   | “iCloud 同步”是本机偏好（`UserDefaults`），不随云居文件或备份恢复                                                                                                         |

## 事务、重试与旧版本限制

新写入口先读取当前用户的历史文档 ID，再在 CloudBase 事务内逐个按 ID 重读，并读取固定的原生文档 ID。事务不使用 `where`。对重读结果重新选择最新版本、计算修订号并比较客户端基线；其他设备已更改时返回 409。所有新写入落在按 UID 的 SHA-256 派生的固定文档中，保留旧历史文档。SDK 非抛出形式的错误码同样使事务失败，不向客户端确认。

同一请求标识、相同内容的成功重试返回已有结果；若旧客户端已改动内容，不把保留的旧请求元数据当作幂等成功。

**仍有跨版本验收缺口**：旧 Web / Capacitor 当前仍通过 JS SDK 直接写入，使用更新时间处理覆盖。CloudBase 文档事务不能锁定查询范围中尚不存在的历史文档；旧客户端在初次查询之后创建新文档的竞态不在现有事务读集内。需要继续统一写入口或完成兼容策略，才能声明全平台并发同步已验收。本轮没有删除历史文档或在线强加唯一索引。

官方限制见 [CloudBase 事务操作](https://docs.cloudbase.net/database/transaction)。
