## 协议与服务

原生运行时不再让 `window.ylf.authorize` 因缺少宿主回调直接返回“授权代理不可用”。`NativeAuthorizationBroker` 连接现有 WebView、中央注册策略、原生登录 / 授权面板与 Keychain 账号服务，不启动隐藏的 CloudBase JS SDK。

| 阶段         | 原生处理                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 收到请求     | 沿用 WKSecurityOrigin 与主 frame 判断；检查精确 HTTPS 来源、同源 redirect URI、client、单一 scope、nonce 与 S256 challenge              |
| 查询注册策略 | 复用 `POST https://apps.yunle.fun/api/auth/sso/resolve`，不附宿主 Bearer token、Cookie 或客户端自报 UID                                 |
| 核对响应     | issuer 固定为 `https://www.yunle.fun`；逐项核对请求回显、策略版本、注册指纹、展示来源和许可描述；名称 / 图标仅取已验证策略              |
| 选择账号     | 已登录账号从原生会话读取；未登录进入原生“登录并继续”；`select_account` 转交既有 ASWebAuthenticationSession                              |
| 用户确认     | `consent` 使用共享的 UIKit 原生授权面板；访客登录完成后总是再次确认，即便此客户端通常属于 trusted                                       |
| 签发 code    | 使用官方 CloudBase Functions OpenAPI：`POST /v1/functions/sso-ticket`，action 为 `issueSsoCode`，Bearer token 只发给固定 CloudBase 网关 |
| 返回网页     | 只返回 `ok`、单次 code、固定 issuer 与合法的可选到期时间；不把原始服务响应、宿主 token、Cookie 或账号资料整包交给页面                   |

网关沿用国内上海环境 `yunlefun-8g7ybcxc7345c490`。本轮先通过 MCP `searchKnowledgeBase(mode="openapi", apiName="functions")` 读取官方路径与鉴权定义，再实现请求；没有根据函数名猜测另一个 HTTP 触发器 URL。现有 `sso-ticket` 云函数和中央注册表仍是服务端权限与一次性 code 的最终依据，本仓库不重写它们。

原生网络会话禁用 Cookie、共享凭据与缓存，并拒绝跟随重定向。HTTP 失败、HTML、非严格布尔值、协议回显替换、非法 prompt / scope / issuer、错误 code 格式均不能被当作成功。首次签码 HTTP 401 可以通过现有账号服务刷新并重试一次，刷新前后都要核对同一个账号。

## 登录回跳与账号隔离

原生登录表单继续使用系统 Form、Picker、SecureField、一次性验证码填充与 Dynamic Type。待授权场景增加可信应用名称，明确显示“登录后返回……，仍需在原生面板确认。登录本身不会自动授权。”；不在 URL 或本地云居文件里保存凭据。

只有一个特定例外允许保留网页：**已经通过注册策略验证、正在等待原生登录的访客请求，转变为已登录账号时**。它保留原 WebView 与原请求，结束其他会话，iOS 17+ 先原子保存该访客仓库的新归属，再重新查询注册策略并展示确认面板；iOS 16 仍等待原有身份 Cookie 允许名单清理。此例外不合并访客云居，不自动授权，也不允许从一个已登录账号延续到另一个账号。

切换 / 退出已登录账号、结束应用、网页导航使请求失效、用户取消或超时，都会撤销对应操作。每次异步结果都重新检查原请求、当前文档和账号；取消后的迟到 code 不能交付给新网页或新账号。一次同时处理一个用户决策，另一个请求不会抢占正在显示的面板。

网络阶段使用 30 秒请求期限，登录和确认使用最长 5 分钟决策期限；作出选择后恢复网络期限。过期会关闭授权 UI。完成 / 取消后清理任务与计时器，计时器不保留已经结束的页面。

“使用其他账号”复用既有系统认证会话、state / nonce / PKCE 与 callback 验证，不替换宿主存储的账号。原生工程已注册现有 `yunlefun` callback scheme，并检查生成的 Debug / Benchmark 应用 Info.plist；这不等于系统账号成功回跳已经验收。

## 已复现的跨账号持久状态与分仓对照 · 2026-10-18 {#persistent-identity-defect}

产品来源 `937bc29`，自有 iPhone 18 Pro / iOS 27 模拟器。新增 `HostIdentitySwitchLiveTests` 默认跳过；仅在显式开关、精确自有模拟器标识及两个固定受管合成账号的一次性私有输入均匹配时运行。它使用真实 `AccountStore`、`NativeWebRuntime`、生产目录及 AI 春联 HTTPS 页面；网页通过 DOM 点击、原生确认通过 UIKit control event 驱动。没有将宿主 token / 密码写入网页，没有创建账号、修改余额或发布内容。这是进程内实际控件旅程，不计作系统手势、原生登录表单或“其他账号”回跳验收。

两次基线均在 A → B 后新建网页的授权前观察到 A 的账号名称。第一轮方法 29.452 秒失败，完成 A 的真实授权，但早期截图尚未绘制、网页退出驱动失败；第二轮收紧为文档加载完成且实际控件存在，额外等待一秒后旧身份仍在，方法 10.148 秒失败。第二轮 A 从缓存恢复，没有本轮新 SSO 请求；宿主强制刷新后的身份匹配，旧运行会话已移除，新浏览器对象已创建。因此，首次绘制和本轮签码迟到都不足以解释该结果。

### 诊断原型的边界（历史）

当时分仓代码仅存在于诊断副本，**没有进入产品或候选包**；后续产品实现见下节。WebKit 官方说明：iOS 17 起可使用多个命名持久仓库，旧系统只有一个默认持久仓库。原型在旧系统回落到内存仓库，这会丢失进程结束后的本地草稿，因此不作为 iOS 16 的完整方案。还需处理未知归属的旧默认仓库、访客登录续接仓库的归属、账号移除与进程重启，以及第二个真实应用和系统其他账号流程。旧数据不得自动归给新账号，也不能通过删除整库宣称修复。

## iOS 17+ 持久分仓与访客续接 · 2026-10-18 {#persistent-web-profiles}

`WebProfileRepository` 以身份提供方、访客 / 账号、应用、信任范围和来源组合绑定随机持久仓库。归属文件原子保存，只含摘要及仓库 UUID，不保存原始 UID、带参数的网址或凭据。每次变更重读磁盘；缺失文件只创建新仓库，损坏、重复归属和未来版本拒绝打开，不回退或自动认领旧默认仓库。此实现仅在 iOS 17+ 使用命名 WebKit 仓库；iOS 16 保留旧路径，已知跨账号持久数据缺陷仍未解决，最低版本没有提高。

宿主切号关闭非续接网页，新账号使用独立仓库。只有授权代理认可的访客登录可以保留同一网页：先把该仓库归属写入账号，再允许重新确认；后来的访客得到新仓库。若账号已存在仓库，两份数据都保留，原账号仓库仍为默认选择，续接仓库进入该账号的保留列表。该阶段尚未提供恢复界面；后续的显式恢复入口见[下节](#web-profile-recovery)。

移除账号先保存仓库脱离状态，再移除本机凭据；保存失败保留账号供重试。重新登录创建新仓库，旧仓库只留在原账号名下，不给访客或其他账号。归属文件与 Keychain 不是跨存储事务：若后续 Keychain 删除失败，仓库可能已脱离，数据仍保留，可通过后续新增的恢复入口选择；真实 Keychain 删除失败后的完整 UI 旅程仍待验证。旧默认仓库不读取、不认领、不整库删除；未知归属的旧数据迁移仍是独立未完成项。
