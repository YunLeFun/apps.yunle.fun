# 寻乐游戏 Tab 与工坊合并：技术设计

日期：2026-10-28。状态：实施中，完成状态以验证证据和任务清单为准。需求依据：[requirements.md](./requirements.md)，任务见 [tasks.md](./tasks.md)。

## 1. 界面与信息层级

### 设计约束

- 目的：在工坊完成云应用发现，在寻乐完成游戏选择、启动和恢复，减少重复页面与输入。
- 视觉方向：有游戏内容特色的原生编辑式页面。使用游戏自己的正式图标、轻量封面和玩法信息，不用装饰素材延迟首屏。
- 色彩：宿主沿用现有动态系统背景、主次文字和品牌强调色；游戏卡片使用正式内容色。浅深色由系统语义色适配，不新增硬编码全局配色。
- 字体：沿用 SwiftUI 语义字体及系统动态字号。项目既定原生设计约束优先于通用 Web UI 技能的字体、配色和破格布局建议。
- 布局：使用原生 TabView / NavigationStack、搜索、列表、菜单、Sheet、ShareLink 和状态页。iPhone 以纵向内容为主，iPad 按可用宽度布局。

### 工坊

默认浏览顺序：搜索与 AI 入口 → 编辑精选 → 分类与有效榜单入口 → 全部应用。控制推荐高度，让搜索与目录容易发现。搜索或筛选时直接呈现结果，不重复展示长推荐区；退出筛选恢复滚动位置。

原生第一切片搬迁现有官方精选与随手发现，随后接通推荐 / 榜单的真实数据及原生助手；Web 的今日推荐、周榜和 AI 内容在 Web 适配阶段搬入工坊。没有真实排行时使用「编辑精选」文案或收起，不沿用静态应用顺序充当 Top 10。

个人工坊的使用继续由云居切换器承接，创作与成员管理保留在「我」，工坊提供次要入口。权限、目录修订和加入流程不因布局合并而改变。

### 寻乐

保持「云居 → 寻乐 → 工坊 → 我」的顺序。寻乐优先展示有效继续对局 / 运行中游戏 → 最近游玩 → 精选游戏 → 全部首批游戏。没有有效房间时不显示空房间卡片。模式与人数筛选放在原生菜单或轻量筛选区。

游戏卡片展示名称、说明、人数、实际可用模式和真实加载状态。主要操作按所选模式直接开始，详情为次要入口。联机提供创建房间、输入房间号和打开邀请；首个可体验切片可先使用 Play 已有房间界面。

## 3. 游戏目录与启动契约

### 对外目录

Play 当前目录是私有 TypeScript 包，尚未核实有供 Swift 使用的公开 JSON 契约。建议构建时导出版本化 JSON，路径在接口切片中确定。以下为新增契约提案，不代表已有 API：

| 字段                                      | 用途                                             |
| ----------------------------------------- | ------------------------------------------------ |
| `schemaVersion`、`catalogVersion`         | 客户端兼容和快照更新                             |
| `gameId`、`appId`、`marketApplicationId?` | 游戏、应用与公开市场身份映射                     |
| 名称、说明、正式图标、封面、人数、类型    | 原生展示                                         |
| `launchModes[]`                           | 明确单人 / 同屏 / 联机的登录与联网要求、启动目标 |
| `resourceManifestURL?`、资源版本          | 可选的公共资源准备能力                           |
| `minimumHostVersion?`、生命周期           | 客户端兼容与停止新启动                           |

iOS 校验 schema、唯一 ID、HTTPS 来源、受控路径、资源预算与支持模式，保留上次成功快照。目录不授予市场、付费、成员或在线房间权限；旧快照只辅助展示，实际启动仍核验有效发布状态与现有访问条件。

Play 的 `kind: native` 表示平台内部 Web 游戏，不代表 Swift 游戏。`launch.localPath` 也不能直接作为通用启动 URL。五子棋电脑对手使用已有 computer 路径；飞行棋未核实有本地入口，先提供真实在线流程，机器人单人也需登录及服务端；星纸按发布情况区分练习、PVE 与联机。

### 启动链路

用户操作 → 校验游戏与模式 → 现有访问 / 授权 → 解析受控启动意图 → 游戏页 → 真实 ready。

首个切片允许联机创建与准备在 Play 页面完成。后续增加受控 launch intent，让原生选择游戏和动作后直达对应界面；导航 GET 只携带意图，不自动重放创房 POST。原生房间控件通过已有 Play 会话中的窄接口或明确支持的接口工作，不把宿主 Bearer 发给 Play，也不复制 Cookie 到原生请求。

原生与 Web 的消息只包含启动、ready、可公开描述的房间状态和可恢复引用。验证来源、主框架、协议版本、账号代次与启动 ID，拒绝旧页面回调。一次性 ticket、Cookie 和宿主凭据不进入目录、日志和历史记录。

## 4. 身份、会话与数据兼容

实施前形成 `gameId → appId / 市场 ID → 运行会话键 → 授权 profile` 的显式映射表，并验证寻乐、云居和邀请三个入口打开同一游戏。

当前 WebRuntime 会话按 `app.id` 索引；网站 profile 还包含应用、来源与运行范围。同域不同 ID 会得到不同 profile，不能依靠换 URL 获得统一 Play 登录。对已登记的第一方 Play 游戏定义可信身份作用域，明确它与聚合入口 `play` 的关系；其他应用继续原有隔离。

迁移先识别旧 profile 与存档，不直接合并 Cookie / IndexedDB，不清空唯一旧数据。无法安全映射时保留旧入口及其数据，并说明兼容行为。先验证数据保留、回退和归属，再接入共享作用域。

最近游玩首批只存本机，按宿主账号 / 访客隔离；游戏 ready 后记一次。云居与最近记录通过身份映射去重，不强制把所有游戏加入云居。

继续对局只保存必要的游戏、房间引用、角色和更新时间，按账号隔离。重连凭据由 Play 的受控运行时处理；App 重启后的恢复不能等同于存活 WebView 的重连。恢复前读取服务端状态；结束、移除或过期后清除无效对局提示。

## 5. 加载与资源准备

顺序为：减少页面跳转与无关代码 → 按游戏准备资源 → 评估有限预热。首期不后台批量启动全部游戏。

现有网页归档只包含捕获时已取得的资源，公共资源策略目前仅允许部分站点与文件类型。Play 需为支持准备的游戏输出资源清单，列明版本、URL、来源、类型、大小、摘要和必需 / 可选关系，覆盖实际使用的 JS、WASM、模型、贴图、字体与音频。跨域来源逐项登记，不按父域名全部放开。

优先验证真实 HTTPS 响应进入游戏实际 WKWebView 所用的缓存，并由系统与原站点响应头控制复用。URLSession 下载到文件不算 WebKit 缓存命中，网页归档不作为完整游戏包，不先引入改写全部 HTTPS 请求的自定义加载器。

先完成五子棋与星纸的验证切片，证明懒加载、跨来源请求、更新、取消、损坏与系统回收均有明确行为，再扩大资源支持。不能可靠复用的资源保持在线加载，不显示虚假的准备完成。

资源准备默认用户主动触发；常玩自动准备为后续选项。沿用 Wi-Fi / 低数据模式偏好，明确单游戏和总预算，大资源超出现有上限时先记录实际体积再决定调整。清理只影响本功能的资源及登记的 HTTP 缓存，不删除账号、网站存储或存档。未经完整验收，不显示全游戏离线承诺。

加载协议区分 navigation、resources、initializing、connecting、ready 与 failed。不可计算阶段显示不定进度，禁止按计时器伪造百分比。

## 6. 邀请、联机与生命周期

复用 `/room/:inviteCode`、Play Cookie 会话、一次性实时 ticket 和 Colyseus 状态。实施时核对源码与实际发布服务的各游戏重连窗口，不套用一个统一时长。

分别处理冷启动邀请、热启动邀请、重复链接、登录取消、账号切换与观战角色。保留跨 App 授权回跳优先级，游戏和房间使用独立的严格目的地解析。Universal Link 需要 Play 域名 AASA 和 App entitlement 配套；尚未部署时保留 Web 路径，不能只改本地解析就认定系统分发完成。

房间状态：未进入 → 登录 / 授权 → 加入中 → 等待玩家 → 进行中 → 重连中 → 已结束 / 失效。收起页面保留会话，结束页面与离开房间分别处理；写操作使用已有幂等能力或结果查询，不盲目重试。

恢复目标是保护期内重新连接并核对服务端快照。iOS 可能挂起后台应用，原生页面不保证永久连接。依据：[Apple 后台执行说明](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)。

## 7. 基线与首批验收目标

同一设备与网络分别测旧入口、新入口、资源已准备和 WebView 存活场景。隔离测试数据与真实存档，不通过擦除在用设备制造冷启动。

| 指标         | 定义与当前目标                                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 点击至可操作 | 原生 tap 至游戏真实 ready；渲染就绪和玩法可操作分别观察，阻止操作的开场倒计时结束前不能上报 ready；每游戏每代表性缓存场景至少 10 次，报告 P50、P90 和样本数                    |
| 加载收益     | 资源准备后的点击至可操作 P50 应优于同条件旧入口，报告实际改进幅度；分别披露固定开场倒计时、资源等待与完整可操作耗时，保留星纸三秒开场规则，不通过提前 ready 或加载动画缩短指标 |
| 启动回归     | 无缓存新路径 P90 不比旧入口劣化超过 10%；导航减少和下载减少分别呈现                                                                                                            |
| 进房闭环     | 首批已发布模式双客户端连续 10 轮有效房间成功，无重复创房 / 占位；无效房间有明确结果                                                                                            |
| 恢复闭环     | 短断网、前后台、Web 进程回收、App 重启分别记录；保护期内恢复或有服务端确认原因，超期不无限重试                                                                                 |
| 资源         | 同版本二次启动避免关键静态资源完整重复传输；动态接口和实时流量单列                                                                                                             |
| 交互         | 星纸记录帧时间、卡顿与内存；大厅响应不作为游戏帧率或 RTT 改善的证明                                                                                                            |

2026-10-29 用户确认保留倒计时并按实际性能报告，加载收益不再统一以降低 30% 阻断验收。初始 30% 工程目标及既有五子棋 21.4%、星纸 8.0% 未达该目标的事实保留；当前标准仍须逐项核对证据，不能因目标调整直接判定完成。

历史 60 样本绑定回环目录 `9ba07032…`，不与后续版本互换；旧冻结目录在完成字节核验后消失，保留当时校验记录，不宣称完整旧字节仍可读取。原拟 926 的一次复测因本地漏依赖而保留为受限事实。随后固定真实 `b25149ae…`／`ed7fe8d8…` 的 377 个正资源文件及实际负响应边界，目录、三清单、选定 HTML 与构建元数据前后双读一致；原生只同步目录 JSON，运行时和无探针导航修复保持不变。N1 六样本与正式 N10 六十样本全部真实进入可操作状态，旧服务日志有并发拼接及异常行，2609 仅为正式窗口可单行解析的 200 响应，不能称完整请求总数或全日志无异常。准备后 P50 五子棋改善 8.31%、星纸 6.48%；星纸直达冷资源 P90 为 5813.09 ms，对照 4536.33 ms，退化 28.15%，因此该历史轮次未通过当前标准。后续 online-only 发布必须说明源范围与测量版本，不把新 live hash 冒称本轮相同字节。

现有 ResourceTiming 仅含主文档已完成条目，不覆盖所有待完成请求及 worker；并行请求时长之和不是资源等待墙钟。原生 uptime 完整耗时与文档 performance 时间分别报告，保留三秒玩法规则，不能跨时钟相减或从总耗时直接减三秒声明资源等待已测得。本轮按现有同一文档时钟的资源与 renderer 观察说明覆盖范围及未知部分，以完整 tap→playing 耗时作为主验收；不新增 Worker／全网路径实验作为本轮门槛。

一次固定 Star-only legacyCold10＋directCold10 诊断复用测试 fixture 的原生阶段 hook，没有产品改动、预热或空白页。该轮未重现原 6.15／5.81 秒异常，只能将自身较慢样本的间隔放在 load 调用返回到原生收到 document-start 之间，不能细分进程、网络、IPC 或 CPU 原因，也不能替换失败 N10。阶段与资源观察、还原证明见[同钟诊断](../../docs/dev/evidence/native-game-discovery/recovery-20261029/m3-star-cold-phase-fixed20-analysis.json)。

此前 online 静态覆盖存在缺口：生成器把 online 模式根设为准备页，通用房间渲染脚本未被导航字符串纳入。最终 `6ff97db…`／`a7011d9f…` 已显式加入 available online 的房间入口及必要静态依赖，未遍历全站 router 动态路由。冻结快照含 261 个游戏资源、379 个正文件，目录、三清单、选定 HTML 和构建元数据共 13 项前后双读一致；三条离线直达 HTML 的必需 JS／CSS 均在相应清单内，非必需 prefetch 另纳入本地闭包。只更新原生目录版本 JSON 后同 DD 单次构建及四文件安装指纹通过，N1 六样本全部真实可玩，1136 条请求均为 200 且无未冻结路径或日志解析缺口，随后一次固定正式六十样本完成：旧入口／冷直达／准备后 P50，五子棋为 1118.37／881.24／833.71 ms，星纸为 4268.49／3909.46／3889.93 ms；准备后对旧入口 P50 分别改善 25.45%／8.87%，冷直达对旧入口 P90 分别改善 17.98%／6.98%。正式窗口 2969 条响应及全服务 4105 条响应均为 200、日志完整解析，性能门槛通过；三秒倒计时与未知网络路径范围保持不变。公开 hash 房间 JS 可准备，动态账号／房间 API 与权威状态仍排除；离线性能测量不代表完整在线旅程。

指标表规定当前验收口径；各轮实测结果仅对应其已记录的版本与测试范围，不构成生产 SLA。模拟器用于旅程与可重复对照；真机性能采样单列，在相应测试范围明确后执行，不把模拟器数据当硬件结论。

## 8. 交付、回退与后续

按「M0 基线 / 契约 → M1 工坊 → M2 原生寻乐 → M3 加载 / M4 联机 → M5 验收 → M6 Web 扩展」执行。目录契约可与工坊并行；身份映射先于正式游戏会话接入，M3 与 M4 可并行。

首批游戏逐项启用。目录、模式或资源策略不兼容时关闭对应能力并保留受控 Web 路径，不影响工坊与云居。缓存失效回在线；房间无效回寻乐并说明原因。回退不删除存档、安装记录或账号数据。

交付记录精确版本、测试证据、基线对照与未覆盖项。新增资源和服务部署独立核验，不把本地完成当线上契约可用。Web / Capacitor 后续采用相同 Tab 语义，macOS / Electron 另做适配；不要求首批一起改完。
